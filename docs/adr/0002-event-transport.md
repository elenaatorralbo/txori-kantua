# 0002 — Transport events over MQTT with versioned JSON and QoS 1

- **Status:** Proposed
- **Proposed on:** 10/11/2026
- **Owner:** Javier Santamaría — [javiers2004](https://github.com/javiers2004)
- **Issue:** [#9](https://github.com/elenaatorralbo/txori-kantua/issues/9)
- **Accepted on:** —

## Context

Four people implement in parallel modules that must fit together: capture and
inference (David), environmental reading and LCD station (Elena), dashboards
and monitoring (Erik), persistence and API (Javier). None of them can wait for
the others to finish, and the hardware is not verified yet, so each module
needs to be developed against a contract and not against an implementation.

A single detection event has at least two consumers with different needs:
persistence wants the whole history and the LCD only wants the latest recent
event. Coupling inference directly to the LCD would force David and Elena to
synchronise their schedules.

## Decision

Every module communicates by publishing and consuming **versioned JSON
messages over MQTT (local Mosquitto) with QoS 1**, following the topics of
[mqtt.md](../mqtt.md). No module calls another one directly or shares its
database.

Rules that follow and are mandatory for everyone:

- The version travels in two places: the topic (`txori/v1/...`) for
  incompatible changes and the `schema_version` field for minor changes. A
  consumer rejects an unknown major version and logs it, but **does not stop**.
- QoS 1 guarantees "at least once", never "exactly once". Duplicates are
  expected behaviour, not a failure: deduplication is the consumer's
  responsibility, through `event_id` ([ADR 0003](0003-persistence.md)).
- `event_id` is generated by the producer **once per logical observation** and
  kept on every retry. Generating a new UUID when retrying is a defect, because
  it turns a resend into a false observation.
- Events do not use `retain`. Only state (`health`, `availability`) is
  retained, and always with a timestamp so the consumer can decide it has
  expired.
- No message carries audio samples, base64, file paths, transcriptions,
  credentials or precise coordinates. It is a contract constraint and it is
  verified by the negative tests of
  [#10](https://github.com/elenaatorralbo/txori-kantua/issues/10).

## Alternatives considered

| Alternative | For | Against | Why it is not chosen now |
|---|---|---|---|
| Direct HTTP calls between processes | No broker to install and no credentials to manage | The producer needs to know and wait for every consumer; adding the LCD forces changes to inference | It prevents parallel work, which is the main constraint of the project |
| A single process with in-memory queues | Trivial deployment, no serialisation | One module failing brings down the others; it prevents moving services to another machine if the Pi is overloaded | Pi overload is a risk already identified in [architecture.md](../architecture.md) and this option closes that door |
| MQTT with QoS 2 | Exactly-once delivery according to the protocol | More network round trips and broker state; it does not solve duplication caused by application retries, which is the real source | Deduplication is needed anyway; QoS 2 adds cost without removing the work |
| Each module writing directly to the database | Fewer pieces | Couples everyone to the schema; several concurrent writers break the single-writer model of [ADR 0003](0003-persistence.md) | It turns the schema into a public interface that cannot be versioned |

## Consequences

- Each module can be developed and tested against JSON fixtures without the
  hardware or the code of the others. This is what allows progress while the
  Pi is still unverified.
- One more service to operate, secure and monitor appears: Mosquitto, with
  per-service ACLs and no anonymous access
  ([#13](https://github.com/elenaatorralbo/txori-kantua/issues/13)).
- Deduplication stops being optional and becomes an acceptance criterion of
  persistence ([#19](https://github.com/elenaatorralbo/txori-kantua/issues/19)).
- There is no global ordering between topics. A consumer cannot assume that an
  environmental event and a detection with close timestamps arrive in that
  order.

## Review criteria

This decision is reopened if any condition is met:

- The p95 latency between publication and reception on the Pi exceeds **1 s**
  in a sustained way with the four producers active.
- Mosquitto uses more than **100 MB** of RSS at rest or prevents meeting the
  resource budget of [ADR 0007](0007-retention.md).
- Event loss with bounded queues and backoff is shown to exceed **1 %** in a
  60 s disconnection, the threshold of
  [#26](https://github.com/elenaatorralbo/txori-kantua/issues/26).
